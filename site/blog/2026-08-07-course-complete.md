## 교재의 파싱 표를 기계로 검증했다

이번 작업에서 가장 잘한 결정이다.

LR 파싱 표는 12×6 = 72칸이다. 손으로 옮겨 적다 보면 한두 칸을 틀리기 쉽고,
**틀린 표로 만든 추적표를 교재에 실으면 학습자가 며칠을 헤맨다.**
"눈으로 검토했다"로는 부족하다고 판단했다.

그래서 파싱 알고리즘을 React와 분리해 `simulate.ts` 로 빼고,
`simulate.test.ts` 에서 확인한다.

```ts
test.each(VALID)('수락: %s', (s) => {
  expect(accepts(simulateLR(exprGrammarLR, exprSLRTable, tok(s)))).toBe(true);
});

test('id + id * id 는 교과서와 같은 축약 순서를 낸다', () => {
  // F→id, T→F, E→T, F→id, T→F, F→id, T→T*F, E→E+T
  expect(reductions).toEqual([6, 4, 2, 6, 4, 6, 3, 1]);
});

test('LL 과 LR 이 같은 언어를 인정한다', () => { /* ... */ });
```

44개 테스트가 통과한다. 그리고 이 축약 순서 `[6,4,2,6,4,6,3,1]` 은
`examples/06-lr-table-driven` 의 C 프로그램이 실제로 출력하는 것과 정확히 같다.
**웹 시뮬레이터와 C 예제가 서로를 검증하는 셈이다.**

## 또 하나의 조용한 버그 — 수식 안의 `$`

지난번 admonition 문제에 이어, 이번에도 "빌드는 통과하는데 틀린" 문제를 만났다.
다만 이번 것은 결국 **빌드를 실패시켜서** 발견됐다.

```
$\mathrm{ACTION}[i, \$] = \textbf{accept}$
```

KaTeX 문법으로는 맞다. 그런데 remark-math가 `\$` 를 이스케이프로 보지 않고
**닫는 구분자로 읽는다**. 결과적으로 수식이 거기서 끊기고,
남은 `\textbf{accept}` 의 `{accept}` 가 MDX 표현식이 되어

```
ReferenceError: accept is not defined
```

로 빌드가 죽었다.

KaTeX에 `$` 를 넣는 방법을 다 확인해 봤는데,

```js
'\\textdollar'  → FAIL (Undefined control sequence)
'\\mathdollar'  → FAIL
'\\$'           → OK   하지만 리터럴 $ 를 포함
'\\char`$'      → OK   역시 리터럴 $ 를 포함
```

전부 리터럴 `$` 를 포함해서 같은 문제를 일으킨다.
그래서 **입력 끝 기호가 들어가는 집합은 수식 대신 코드 스팬으로** 쓰기로 했다.

```md
FOLLOW(E) = `{ +, ), $ }`
```

이 김에 `onBrokenLinks` 와 `onBrokenAnchors` 를 `'throw'` 로 되돌렸다.
장 사이 상호 참조가 100개가 넘는 교안이라, 링크 검사가 사실상 회귀 테스트다.

한국어 앵커 슬러그에서도 두 번 걸렸다.
`### 모호성 제거 ② — dangling else` 의 슬러그는
`모호성-제거---dangling-else` 로 **하이픈이 셋**이다.
`②` 와 `—` 가 각각 제거되면서 공백 셋이 남기 때문인데,
직접 세어 보지 않으면 맞히기 어렵다. 빌드가 잡아 준다.

## 예제도 서로를 검증한다

05번(재귀 하강)과 06번(표 구동 LR)은 **같은 언어**를 파싱한다.
같은 입력에 같은 답을 내야 한다. 07번(flex+bison)도 마찬가지다.

세 파서를 나란히 두니 교안에서 하고 싶었던 말이 저절로 드러났다.

| | 05 재귀 하강 | 06 표 구동 LR | 07 flex+bison |
|---|---|---|---|
| 문법 | 좌재귀 제거 필요 | 좌재귀 그대로 | **모호해도 됨** |
| 결합성 | 액션에서 접음 | 문법이 결정 | **선언 한 줄** |
| 표 | 없음 | **손으로 작성** | 자동 생성 |
| 문법 변경 | 함수 수정 | **표 재작성** | 규칙 한 줄 |
| 오류 메시지 | 문맥을 안다 | 기대 토큰 | 기대 토큰 |

06번의 72칸짜리 표를 손으로 유지할 수 없다는 것이 yacc의 존재 이유이고,
05번의 오류 메시지 품질이 GCC·Clang·Rust·Go가 **여전히 손으로**
재귀 하강 파서를 쓰는 이유다. 둘 다 직접 만들어 보면 납득이 된다.

## bison 버전과 우선순위에서 겪은 것

`07-yacc-calc` 에서 처음엔 `-2 ^ 2` 가 `4` 를 냈다.
`%right UMINUS` 를 `%right '^'` **아래**에 두어서,
UMINUS가 `^` 보다 높은 우선순위를 가졌기 때문이다.

수학과 파이썬(`-2**2 == -4`) 관례를 따르려면 반대여야 한다.
순서를 바꾸니 `-4` 가 나왔고, 문서의 설명과도 맞게 됐다.
**우선순위 선언의 순서가 곧 의미론이라는 것**을 예제가 직접 보여 주게 됐다.

줄 번호에서도 한 번 걸렸다. `1 / 0` 오류가 9행 대신 10행으로 보고됐는데,
원인은 flex의 `yylineno` 가 `\n` 을 매치하는 **즉시** 증가하기 때문이다.
그 `\n`(EOL)은 파서가 lookahead로 먼저 읽어 두므로,
`expr '/' expr` 축약의 액션이 실행될 때는 이미 한 줄 앞서 있다.
줄 번호를 파서가 직접 세도록 바꿔서 해결했고, 그 이유를 코드 주석에 남겼다.

## 6부에서 정한 관점

최신 동향을 쓰면서 하나를 분명히 하고 싶었다.

> **LLM이 성과를 낸 곳은 최적화 휴리스틱 탐색과 auto-tuning이다.
> 어휘·구문 분석처럼 결정론적 정확성이 필요한 영역은
> 여전히 형식 문법 + 생성기의 것이다.**

두 문제의 성격이 다르다.
"어떤 최적화 패스를 어떤 순서로 적용할까"는 정답이 여럿이고
실행해 봐야 아는 탐색 문제다 — LLM이 잘하는 종류다.
"`int x = 1;` 을 파싱하라"는 정답이 하나이고 틀리면 안 된다 —
DFA가 확실하고 빠르고 증명 가능하다.

CompCert가 좋은 방증이다. 42,000줄의 Coq로 C 컴파일러를 검증하면서
**파서는 검증 대상에서 뺐다**. Menhir가 이미 검증된 LR(1) 파서를 만들어 주기 때문이다.
이론이 확립되어 있다는 것의 실용적 가치가 여기 있다.
