## 14장 — 표의 어느 칸을 보고 있는지

연산자 우선순위 파싱의 요점은 한 줄이다.

> 우선순위가 **표의 한 칸**으로 표현되고, 그것이 파스 트리를 결정한다.

그러면 그 칸을 눈으로 좇을 수 있어야 한다.
스테퍼를 만들면서 우선 관계 표를 옆에 함께 그리고,
**지금 비교 중인 행·열과 칸**을 강조하게 했다.

`id + id * id` 의 6단계에서 이렇게 된다.

```
스택 $ E + E    입력 * id $    관계 + ⋖ *    동작 이동 *
```

표의 `+` 행 `*` 열이 밝게 표시된다.
그 칸이 ⋗ 였다면 `E + E` 를 먼저 축약해 `(a+b)*c` 가 됐을 것이다.

우결합 `^` 를 넣은 두 번째 표도 함께 뒀다.
`id ^ id ^ id` 를 돌려 보면 **`id` 셋을 다 쌓은 뒤에야** 축약이 시작된다.
`+` 는 두 번째 `id` 에서 바로 축약이 일어난다. 결합성의 차이가 눈에 보인다.

## 17장 — 후위 순회 순위라는 열 하나

17장의 결론은 이것이다.

> LR(yacc)은 값을 위로 올리기에 강하고, LL은 아래로 내리기에 강하다.

이걸 보여 주려고 속성 평가 스테퍼를 만들었는데,
결정적인 것은 표의 **마지막 열 하나**였다 — 그 속성이 붙은 노드의
**후위 순회 순위**.

**합성 속성 (`3 * 5 + 4`)**

```
 1  num.val   합성   어휘 분석기가 준다        3     후위 0
 2  F.val     합성   F.val := num.val         3     후위 1
 3  T.val     합성   T.val := F.val           3     후위 2
 ...
11  E.val     합성   E.val := E₁.val + T.val  19    후위 12
```

`0, 1, 2, 4, 5, 6, 7, 9, 10, 11, 12` — **계속 커지기만 한다.**
계산 순서가 곧 후위 순회 순서라는 뜻이고,
LR 파서가 축약하는 순서가 후위 순회이므로 **파싱 중에 값이 다 정해진다.**

**상속 속성 (`int a, b, c`)**

```
 1  T.type     합성   T.type := integer         integer      후위 1
 2  L.in       상속   L.in := T.type            integer      후위 9
 3  L.in       상속   L₁.in := L.in             integer      후위 6
 4  L.in       상속   L₁.in := L.in             integer      후위 3
 5  L.addtype  액션   addtype(id.entry, L.in)   a : integer  후위 3
```

`1, 9, 6, 3, 3, 6, 9` — **오르내린다.**

이유는 트리 모양이다. `L → L₁ , id` 가 왼쪽 재귀라
가장 왼쪽 이름 `a` 가 가장 깊은 곳에 놓이는데,
`a` 의 타입은 트리 꼭대기의 `T` 에서 와야 한다.

후위 순회는 `a` 를 먼저 방문한다. 그때 `T.type` 은 아직 없다.

**이 오르내림이 yacc에서 중간 액션이나 전역 버퍼가 필요해지는 이유다.**
19장 미니 컴파일러의 `pending_add()` / `pending_flush()` 가 이 문제의 우회였다.

## 두 번 구현해서 맞춰 보기

두 컴포넌트의 알고리즘은 React 밖의 순수 함수로 뒀다.
그리고 **같은 것을 C로 한 번 더** 만들었다.

- `examples/10-operator-precedence` — 우선 관계 표를 `PREC[6][6]` 배열로
- `examples/11-attribute-eval` — 파스 트리 + 의존 그래프 + 위상 정렬

`10` 은 `06-lr-table-driven` 과 입출력 형식을 맞췄다.
같은 식을 두 파서에 넣으면 이렇게 대조된다.

| | SLR (예제 06) | 연산자 우선순위 (예제 10) |
|---|---|---|
| 표 크기 | 12 상태 × 9 열 | **6 × 6** |
| 스택 | 심볼 + **상태 번호** | 심볼만 |
| 결정 근거 | 스택 맨 위 **상태**와 입력 | 스택 맨 위 **터미널**과 입력 |
| 문법 | $E/T/F$ 로 계층화 필요 | 모호해도 된다 |

둘 다 14를 낸다. LR은 문맥을 상태 번호에 담고,
연산자 우선순위 파싱은 표의 한 칸에 담는다.

`11` 은 웹 컴포넌트와 **같은 판정**을 한다.

```
입력: int a, b, c
  후위 순회 한 번으로: 불가능
    막히는 곳: L.in 는 자기 후손 밖의 값을 필요로 한다
```

TypeScript와 C로 두 번 구현해 결과가 같은지 확인한 셈이다.
테스트는 44개에서 **87개**로 늘었다.

## 내가 지난번에 만든 버그

용어 사전 127개 항목 전부에 대해
"한국어 표기가 링크한 장의 본문에 실제로 있는가"를 확인했다.

```
★ 본문에 없는 용어
  완전 DFA         → /docs/regular/finite-automata
  스캐너 / 토크나이저  → /docs/foundations/compiler-overview
  동등 클래스        → /docs/regular/representations
  결정적 CFL        → /docs/parsing/context-free-grammar
  하향식 파싱        → /docs/parsing/syntax-analysis
```

`완전 DFA` 는 **지난 감사에서 내가 추가한 항목**이다.
본문은 "전함수(total function)"라고 쓰는데 사전에는 없는 말을 올려 뒀다.

1차 감사 때 "용어 사전이 7장을 가리키는데 그 장에 렉심이라는 단어가 없다"를
잡았었다. 같은 버그를 내가 다시 만든 것이다.

그래서 이번에는 **lint 규칙 8번**으로 넣었다.

```ts
// 사전에 올린 한국어 표기가 링크한 장의 본문에 실제로 있어야 한다.
// 없다면 둘 중 하나다 — 본문 표기와 다른 말을 지어냈거나,
// 링크가 엉뚱한 장을 가리키거나.
if (body && !body.includes(term)) { … }
```

일부러 `전함수` 를 `완전 DFA` 로 되돌려 놓고 lint가 잡는지 확인한 뒤 되살렸다.

## 남는 생각

세 번의 감사에서 매번 **같은 종류의 결함**이 나왔다.

1차 — 내용이 빠졌다
2차 — 렌더링이 조용히 깨졌다
3차 — **자산이 장마다 고르지 않고, 만든 것이 연결되지 않았다**

세 번 다 "글을 읽어서" 찾은 게 아니라 **세어서** 찾았다.
lint 규칙이 8개가 됐는데, 전부 한 번씩 실제로 겪은 것들이다.

```bash
cd site && bun run check      # lint(8) + typecheck + 87 tests + build
cd examples && make test      # 11개 예제 34케이스
```
