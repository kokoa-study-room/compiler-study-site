# 14. 연산자 우선순위 파싱

[13장](/docs/parsing/ll-parsing)의 하향식 파싱을 보았으니 이제 상향식이다.
그런데 상향식의 대표인 LR은 표가 커서 손으로 만들기 어렵다.

**연산자 우선순위 파싱(operator-precedence parsing)** 은
그 사이에 있는 방법이다.

- 상향식이다 (이동-축약)
- **표가 아주 작다** — 터미널 × 터미널 크기
- **손으로 만들 수 있다**
- 대신 **아주 좁은 문법에만** 쓸 수 있다

식(expression)을 파싱하는 데 특화된 기법이라고 보면 된다.
실제로 초기 FORTRAN 컴파일러들이 이 방식을 썼고,
지금도 손으로 쓴 파서에서 **식 부분만** 이 방법으로 처리하는 경우가 많다.

:::info[왜 지금 배우는가]
1. **상향식 파싱의 감각을 싼값에 얻는다.**
   "언제 축약하는가"라는 LR의 핵심 질문을, 훨씬 작은 표로 먼저 만난다.
2. **yacc의 `%left` / `%right` 선언이 무엇을 하는 것인지** 이해하는 데 직결된다.
   [20장](/docs/yacc/conflicts-and-precedence)에서 이 이야기가 다시 나온다.
3. 이 기법의 **한계**가 곧 LR이 필요한 이유다.
:::

## 14.1 연산자 문법

이 기법은 아무 문법에나 쓸 수 없다. **연산자 문법**이어야 한다.

:::info[정의 — 연산자 문법 (operator grammar)]

문맥 자유 문법 $G$ 가 다음 두 조건을 만족하면 **연산자 문법**이다.

1. **$\varepsilon$ 생성 규칙이 없다**
2. **우변에 넌터미널이 두 개 연속으로 나오지 않는다**

즉 모든 우변이 `A a B`, `a A b`, `a` 처럼
넌터미널 사이에 반드시 터미널이 끼어 있어야 한다.
:::

**예제 — 연산자 문법인 것**

$$
E \to E + E \mid E - E \mid E * E \mid E / E \mid (\,E\,) \mid \mathbf{id}
$$

$E + E$ 에서 두 $E$ 사이에 `+` 가 있다. `(E)` 도 양쪽이 터미널이다. ✅

:::tip[모호한 문법을 그대로 쓴다는 데 주목]
위 문법은 **모호하다**. `id + id * id` 에 파스 트리가 둘 이상이다.

[2장에서 본](/docs/foundations/language-and-grammar#24-모호성) 계층화된
$E/T/F$ 문법 대신 이것을 쓰는 이유는, 모호성을 **문법이 아니라 표**로
해소할 것이기 때문이다.

이것이 [18장 yacc](/docs/yacc/yacc-overview#187-첫-번째-파서--계산기)에서
`%left` 선언으로 하는 일과 정확히 같은 발상이다.
:::

**예제 — 연산자 문법이 아닌 것**

$$
S \to \mathbf{if}\ E\ \mathbf{then}\ S\ \mathbf{else}\ S
$$

`S else S` — 아니, 여기는 사이에 `else` 가 있으니 괜찮다. 그러나

$$
E \to E\ T \mid T, \qquad T \to \mathbf{id}
$$

$E\,T$ 에서 넌터미널 둘이 **연속**한다. ❌ 연산자 문법이 아니다.

함수 적용 `f x` 처럼 연산자 없이 나열하는 언어(Haskell, ML)는
이 기법을 쓸 수 없다.

## 14.2 우선 관계

핵심 아이디어는 이것이다.

> **인접한 두 터미널 사이에 "누가 먼저 묶이는가"를 표시해 둔다.**

세 가지 관계를 쓴다.

| 관계 | 읽는 법 | 뜻 |
|---|---|---|
| $a \lessdot b$ | $a$ 가 $b$ 에게 **양보한다** | $b$ 쪽이 먼저 묶인다 (핸들이 $b$ 뒤에서 시작) |
| $a \doteq b$ | $a$ 와 $b$ 가 **같은 핸들 안에 있다** | 예: `(` 와 `)` |
| $a \gtrdot b$ | $a$ 가 $b$ 를 **이긴다** | $a$ 쪽이 먼저 묶인다 (핸들이 $a$ 에서 끝남) |

:::caution[수학의 `<` `=` `>` 와 다르다]
$\lessdot$, $\doteq$, $\gtrdot$ 는 **대소 관계가 아니다**.
- 대칭이 아니다: $a \lessdot b$ 라고 해서 $b \gtrdot a$ 인 것은 아니다
- 셋 중 **둘 이상**이 동시에 성립할 수도, **하나도** 성립하지 않을 수도 있다
  (하나도 없으면 그것이 구문 오류다)

기호 옆의 점(`·`)이 "이건 보통 부등호가 아니다"라는 표시다.
:::

### 우선순위와 결합성에서 표 만들기

연산자마다 **우선순위 등급**과 **결합 방향**을 정하면 관계가 결정된다.

```
같은 줄에 있는 연산자 a, b 에 대해:

  a 의 우선순위 < b 의 우선순위   →   a ⋖ b      (b 가 더 세니 먼저 묶인다)
  a 의 우선순위 > b 의 우선순위   →   a ⋗ b
  우선순위가 같고 좌결합          →   a ⋗ b      (왼쪽부터 묶는다)
  우선순위가 같고 우결합          →   a ⋖ b      (오른쪽부터 묶는다)
```

**예제 문법**

$$
E \to E + E \mid E * E \mid (\,E\,) \mid \mathbf{id}
$$

- `+` : 우선순위 1, 좌결합
- `*` : 우선순위 2, 좌결합
- `id`, `(`, `)`, `$` 는 별도 규칙

**완성된 우선 관계 표**

|  | `+` | `*` | `(` | `)` | `id` | `$` |
|---|---|---|---|---|---|---|
| **`+`** | ⋗ | ⋖ | ⋖ | ⋗ | ⋖ | ⋗ |
| **`*`** | ⋗ | ⋗ | ⋖ | ⋗ | ⋖ | ⋗ |
| **`(`** | ⋖ | ⋖ | ⋖ | ≐ | ⋖ | |
| **`)`** | ⋗ | ⋗ | | ⋗ | | ⋗ |
| **`id`** | ⋗ | ⋗ | | ⋗ | | ⋗ |
| **`$`** | ⋖ | ⋖ | ⋖ | | ⋖ | |

행이 **왼쪽 터미널**, 열이 **오른쪽 터미널**이다. 빈 칸은 **구문 오류**다.

**한 칸씩 읽어 보자.**

| 칸 | 값 | 이유 |
|---|---|---|
| `+` 행 `*` 열 | ⋖ | `*` 가 더 세다. `a + b * c` 에서 `b * c` 가 먼저 묶여야 한다 |
| `*` 행 `+` 열 | ⋗ | `a * b + c` 에서 `a * b` 가 먼저 |
| `+` 행 `+` 열 | ⋗ | 같은 우선순위 + 좌결합 → 왼쪽부터. `(a+b)+c` |
| `(` 행 `)` 열 | ≐ | 둘이 한 핸들 `(E)` 안에 있다 |
| `id` 행 아무 열 | ⋗ | `id` 는 언제나 즉시 축약된다 (가장 먼저 묶임) |
| `$` 행 아무 열 | ⋖ | 입력 시작은 모든 것에 양보한다 |
| `)` 행 `(` 열 | (빈칸) | `)(` 는 올 수 없다 → 오류 |

:::tip[우결합이면 반대다]
거듭제곱 `^` 를 우결합으로 두면 `^` 행 `^` 열이 **⋖** 가 된다.
`2^3^2` 가 `2^(3^2)` 로 묶인다.

[20장 yacc의](/docs/yacc/conflicts-and-precedence#203-우선순위와-결합성-선언)
`%right '^'` 가 표의 이 한 칸을 바꾸는 것과 같다.

아래 표에서 `^` 행 `^` 열이 ⋖ 인 것을 확인하고,
`id ^ id ^ id` 를 돌려 보자. **`id` 셋을 다 쌓은 뒤에야** 축약이 시작된다 —
오른쪽부터 묶인다는 뜻이다. `+` 는 두 번째 `id` 에서 바로 축약이 일어난다.

## 14.3 파싱 알고리즘

관계 표만 있으면 파싱은 아주 단순하다.

:::info[알고리즘]
```
스택 ← [$]
입력 ← 토큰들 + $

반복:
    a ← 스택 맨 위의 **터미널**   (넌터미널은 건너뛴다)
    b ← 현재 입력 토큰

    a ≐ b  또는  a ⋖ b   →  b 를 스택에 밀어 넣고 입력을 하나 전진   (이동)
    a ⋗ b                →  축약:
                              스택에서 ⋖ 를 만날 때까지 걷어 낸다
                              걷어 낸 부분이 핸들이다
    a = b = $            →  수락
    관계가 없음           →  구문 오류
```
:::

**핵심 두 가지.**

**① 스택 맨 위의 "터미널"을 본다.**
스택에는 넌터미널도 쌓이지만, 관계 표는 터미널 사이에만 정의되어 있다.
그래서 넌터미널을 건너뛰고 가장 위의 터미널을 찾는다.

**② 핸들을 찾는 방법이 명확하다.**
$\gtrdot$ 를 만나면 축약할 때가 온 것이고,
**$\lessdot$ 가 나올 때까지** 걷어 내면 그 구간이 정확히 핸들이다.

```
… ⋖ (핸들) ⋗ …
    ↑ 여기부터  ↑ 여기까지
```

### 손으로 돌려 보기 — `id + id * id`

| 스택 | 입력 | 관계 | 동작 |
|---|---|---|---|
| `$` | `id + id * id $` | `$` ⋖ `id` | 이동 |
| `$ id` | `+ id * id $` | `id` ⋗ `+` | **축약** `E → id` |
| `$ E` | `+ id * id $` | `$` ⋖ `+` | 이동 |
| `$ E +` | `id * id $` | `+` ⋖ `id` | 이동 |
| `$ E + id` | `* id $` | `id` ⋗ `*` | **축약** `E → id` |
| `$ E + E` | `* id $` | `+` ⋖ `*` | 이동 ← **여기가 핵심** |
| `$ E + E *` | `id $` | `*` ⋖ `id` | 이동 |
| `$ E + E * id` | `$` | `id` ⋗ `$` | **축약** `E → id` |
| `$ E + E * E` | `$` | `*` ⋗ `$` | **축약** `E → E * E` |
| `$ E + E` | `$` | `+` ⋗ `$` | **축약** `E → E + E` |
| `$ E` | `$` | — | **수락** |

### 직접 돌려 보기

표의 어느 칸을 보고 있는지가 함께 강조된다.
**`id + id * id` 의 6단계**를 눌러 보면, 스택이 `$ E + E` 이고 입력이 `*` 일 때
`+` 행 `*` 열의 ⋖ 하나 때문에 축약하지 않고 이동한다는 것을 볼 수 있다.

<OperatorPrecedenceParser
  grammar={opGrammar}
  table={opPrecTable}
  order={opTerminalOrder}
  defaultInput="id + id * id"
  samples={[
    'id + id * id',
    'id * id + id',
    '( id + id ) * id',
    'id + id + id',
    'id id',
  ]}
  title="연산자 우선순위 파서 — E → E + E | E * E | ( E ) | id"
/>

:::tip[`id id` 를 눌러 보자]
`id` 행 `id` 열은 **빈 칸**이다. 피연산자 둘이 붙을 수 없다는 뜻이고,
표가 그 자리에서 바로 구문 오류를 낸다.

LR 표에서 빈 칸이 오류인 것과 같은 원리인데,
여기서는 표가 **터미널 × 터미널** 이라 훨씬 작다.
:::

:::danger[6행이 이 장의 요점이다]
스택이 `$ E + E` 이고 입력이 `*` 일 때, 스택 맨 위의 **터미널**은 `+` 다.
표에서 `+` 행 `*` 열을 보면 **⋖** — 이동한다.

만약 `+` 행 `*` 열이 ⋗ 였다면 `E + E` 를 먼저 축약해
`(a + b) * c` 가 되었을 것이다.

**연산자 우선순위가 표의 한 칸으로 표현되고, 그것이 파스 트리를 결정한다.**
[15장 LR](/docs/parsing/lr-parsing#151-이동-축약-파싱)의 9행과
정확히 같은 상황이고, 같은 결론이다.
:::

### 축약할 때 "무엇으로" 축약하는가

눈치챘을 수도 있는데, 위 표에서 `E → id` 인지 `E → E * E` 인지를
**관계 표는 알려 주지 않는다**.

이 기법은 핸들의 **위치**만 찾아 준다.
무엇으로 축약할지는 걷어 낸 심볼 열을 보고 문법에서 찾아야 한다.

다행히 연산자 문법에서는 이것이 쉽다.
걷어 낸 것이 `id` 면 `E → id`, `E * E` 면 `E → E * E` 다.

:::note[그래서 넌터미널 이름이 필요 없다]
연산자 우선순위 파싱은 **넌터미널을 구별하지 않는다**.
스택에 쌓이는 넌터미널을 전부 그냥 `E`(또는 아무 표시)로 둬도 파싱이 된다.

이것이 이 기법이 그토록 간단한 이유이자, 동시에 **한계**다.
넌터미널을 구별하지 못하므로 `E`, `T`, `F` 를 나눠 쓰는 문법에는 쓸 수 없다.
:::

## 14.4 우선 함수

표를 그대로 두면 터미널이 $n$ 개일 때 $n^2$ 칸이 필요하다.
**우선 함수(precedence function)** 로 이것을 $2n$ 으로 줄일 수 있다.

두 함수 $f$(왼쪽용)와 $g$(오른쪽용)를 정수로 정의해서

$$
\begin{aligned}
a \lessdot b &\iff f(a) < g(b) \\
a \doteq b &\iff f(a) = g(b) \\
a \gtrdot b &\iff f(a) > g(b)
\end{aligned}
$$

가 되게 만든다.

**위 표에 대한 우선 함수**

| | `+` | `*` | `(` | `)` | `id` | `$` |
|---|---|---|---|---|---|---|
| $f$ | 2 | 4 | 0 | 6 | 6 | 0 |
| $g$ | 1 | 3 | 5 | 0 | 5 | 0 |

**검산해 보자.**

| 관계 | 확인 |
|---|---|
| `+` ⋖ `*` | $f(+) = 2 < g(*) = 3$ ✅ |
| `*` ⋗ `+` | $f(*) = 4 > g(+) = 1$ ✅ |
| `+` ⋗ `+` | $f(+) = 2 > g(+) = 1$ ✅ (좌결합) |
| `(` ≐ `)` | $f(() = 0$, $g()) = 0$ ✅ |
| `id` ⋗ `$` | `f(id) = 6 > g($) = 0` ✅ |

:::caution[우선 함수가 항상 존재하지는 않는다]
표를 함수 두 개로 압축하면 **정보가 손실된다**.

원래 표의 **빈 칸(오류)** 이 사라진다. $f(a)$ 와 $g(b)$ 는 언제나
비교 가능한 정수이므로, 오류여야 할 조합에도 관계가 생겨 버린다.

```
`)` 행 `(` 열은 원래 오류인데,
f()) = 6 > g(() = 5 이므로 ⋗ 로 읽힌다.
```

그래서 우선 함수를 쓰면 **오류 검출이 늦어진다**.
잘못된 입력이 몇 단계 더 진행된 뒤에야 발각된다.

또한 어떤 표는 아예 우선 함수로 표현할 수 없다.
(존재 여부는 유향 그래프의 사이클 검사로 판정한다.)
:::

## 14.5 한계 — 그래서 LR이 필요하다

### 한계 ① 연산자 문법만 가능

$\varepsilon$ 규칙이 없어야 하고, 넌터미널이 연속하면 안 된다.
실제 프로그래밍 언어의 문법 대부분이 이 조건을 어긴다.

```
stmt_list : /* 없음 */          ← ε 규칙. ❌
          | stmt_list stmt      ← 넌터미널 연속. ❌
          ;
```

**식(expression) 이외의 문법에는 사실상 쓸 수 없다.**

### 한계 ② 넌터미널을 구별하지 못한다

$E$, $T$, $F$ 를 나눠 의미를 다르게 주는 문법을 다룰 수 없다.
파싱은 되지만 어느 규칙으로 축약할지 알 수 없어진다.

### 한계 ③ 단항 마이너스

```
a - b        이항 뺄셈
- b          단항 부정
```

같은 터미널 `-` 인데 문맥에 따라 우선순위가 달라야 한다.
표는 터미널 하나에 관계 하나만 줄 수 있으므로 표현할 수 없다.

**실무적 우회:** 스캐너가 문맥을 보고 단항 마이너스를 **다른 토큰**
(`UMINUS`)으로 반환한다.

:::tip[yacc의 `%prec UMINUS` 가 바로 이것이다]
[20장](/docs/yacc/conflicts-and-precedence#prec--규칙의-우선순위를-직접-지정)의

```c
| '-' expr %prec UMINUS   { $$ = -$2; }
```

는 "이 규칙만은 `-` 가 아니라 `UMINUS` 의 우선순위를 쓰라"는 뜻이다.
연산자 우선순위 파싱의 이 오래된 문제를, yacc는 문법 쪽에서 해결한다.
:::

### 한계 ④ 잘못된 입력을 받아들일 수 있다

관계 표는 넌터미널을 보지 않으므로,
문법에 없는 문장을 파싱해 버리는 경우가 생긴다.

```
id id        ← 관계 표만 보면 걸러지지 않을 수 있다
```

축약 시 실제 문법 규칙과 대조하는 검사를 따로 넣어야 한다.

## 14.6 실습 — 표를 C 배열로

`examples/10-operator-precedence` 가 위 표를 그대로 옮긴 파서다.

```bash
cd examples/10-operator-precedence
make
echo "2 + 3 * 4" | ./opprec -t
```

```
   # | stack                        | input          | relation | action
   1 | $                            | 2 + 3 * 4 $    | $ < num | 이동 num
   2 | $ num                        | + 3 * 4 $      | num > + | 축약 E -> num
   ...
   6 | $ E + E                      | * 4 $          | + < *   | 이동 *
   ...
  11 | $ E                          | $              | -       | 수락
  값: 14
```

표는 이렇게 생겼다.

```c
/*          num   +    *    (    )    $      */
static const unsigned char PREC[NTERM][NTERM] = {
/* num */ { NONE, GT,  GT,  NONE, GT,  GT   },
/* +   */ { LT,   GT,  LT,  LT,   GT,  GT   },
/* *   */ { LT,   GT,  GT,  LT,   GT,  GT   },
/* (   */ { LT,   LT,  LT,  LT,   EQ,  NONE },
/* )   */ { NONE, GT,  GT,  NONE, GT,  GT   },
/* $   */ { LT,   LT,  LT,  LT,   NONE, NONE },
};
```

**14.2절의 표와 한 칸씩 대응한다.** `NONE` 이 빈 칸이다.

:::tip[한 칸을 바꿔 보자]
`+` 행 `*` 열을 `LT` 에서 `GT` 로 바꾸고 다시 빌드하면
`2 + 3 * 4` 가 **20** 이 된다. `(2+3)*4` 로 묶인 것이다.

우선순위가 표의 한 칸이라는 말이 비유가 아님을 직접 확인할 수 있다.
:::

같은 식을 두 파서에 넣어 보자.

| | `06-lr-table-driven` (SLR) | `10-operator-precedence` |
|---|---|---|
| 표 크기 | 12 상태 × 9 열 | **6 × 6** |

| 결정 근거 | 스택 맨 위 **상태**와 입력 | 스택 맨 위 **터미널**과 입력 |
| 문법 | $E/T/F$ 로 계층화해야 | 모호해도 된다 |
| 넌터미널 | `E`, `T`, `F` 구별 | **전부 `E` 하나** |

둘 다 14를 낸다. LR은 문맥을 **상태 번호**에 담고,
연산자 우선순위 파싱은 **표의 한 칸**에 담는다.

## 14.7 정리 — 세 파싱 기법의 위치

| | LL(1) | 연산자 우선순위 | LR(1) |
|---|---|---|---|
| 방향 | 하향식 | **상향식** | 상향식 |
| 표 크기 | 넌터미널 × 터미널 | **터미널 × 터미널** | 상태 × 심볼 |
| 손으로 만들기 | 가능 | **쉽다** | 사실상 불가능 |
| 문법 제약 | 좌재귀 ❌, 공통 접두사 ❌ | **연산자 문법만** | 거의 없음 |
| 넌터미널 구별 | 한다 | **못 한다** | 한다 |
| 오류 검출 | 빠르다 | 늦다 (특히 우선 함수) | 가장 빠르다 |
| 실무 용도 | 언어 전체 | **식 부분만** | 언어 전체 |

:::info[지금도 쓰인다 — Pratt 파싱]
연산자 우선순위 파싱의 현대적 변형이 **Pratt 파싱**
(top-down operator precedence)이다.

재귀 하강 파서 안에서 **식 부분만** 우선순위 기반으로 처리한다.
문장·선언은 재귀 하강으로, 식은 Pratt으로 — 이 조합이
손으로 쓴 파서의 표준 구조다.

Go, Rust, TypeScript, Clang의 식 파서가 이 방식이다.
[13장의 재귀 하강](/docs/parsing/ll-parsing#131-재귀-하강-파싱)에서
`parse_term` 이 `while` 로 같은 우선순위를 처리한 것이 그 가장 단순한 형태다.
:::

## 요약

- **연산자 우선순위 파싱**은 손으로 만들 수 있는 가장 간단한 상향식 파서다.
  표 크기가 **터미널 × 터미널** 뿐이다.
- **연산자 문법**에만 쓸 수 있다 — ε 규칙이 없고, 넌터미널이 연속하지 않아야 한다.
- 세 관계 $\lessdot$(양보), $\doteq$(같은 핸들), $\gtrdot$(이김)로
  인접 터미널 사이의 결합 방향을 표시한다.
  **대소 관계가 아니고 대칭도 아니다.**
- 우선순위가 같을 때 **좌결합이면 ⋗, 우결합이면 ⋖** 다.
- 파싱: $\lessdot$ 나 $\doteq$ 면 이동, $\gtrdot$ 면 **$\lessdot$ 가 나올 때까지 걷어 내어** 축약.
- **우선 함수** $f, g$ 로 표를 $n^2$ 에서 $2n$ 으로 줄일 수 있으나,
  **빈 칸(오류)이 사라져 오류 검출이 늦어진다**.
- 한계: 연산자 문법 전용, 넌터미널 구별 불가, 단항 연산자 문제,
  잘못된 입력을 받아들일 수 있음. → **그래서 LR이 필요하다.**
- 현대적 변형인 **Pratt 파싱**은 재귀 하강 파서의 식 부분에 지금도 널리 쓰인다.

## 확인 문제

1. 다음 문법이 연산자 문법인지 판정하라.
   - (a) $E \to E + T \mid T$, $T \to T * F \mid F$, $F \to \mathbf{id}$
   - (b) $S \to a S b \mid \varepsilon$
   - (c) $L \to L , E \mid E$, $E \to \mathbf{id}$

<details>
<summary>풀이</summary>

**(a) 아니다.** 조건 2는 만족하지만($E + T$ 사이에 `+`, $T * F$ 사이에 `*`),
$E \to T$ 와 $T \to F$ 는 우변이 넌터미널 하나뿐이다.

사실 이 규칙들은 조건 2("넌터미널 **둘이 연속**")를 어기지는 않는다.
그러나 연산자 우선순위 파싱은 **넌터미널을 구별하지 못하므로**
$E \to T$ 와 $T \to F$ 같은 단일 생성 규칙을 처리할 수 없다.
형식적으로는 연산자 문법이지만 **실질적으로 쓸 수 없다**.

**(b) 아니다.** $\varepsilon$ 생성 규칙이 있으므로 조건 1 위반.

**(c) 맞다.** $L\,,\,E$ 는 넌터미널 사이에 `,` 가 있고,
$L \to E$ 와 $E \to \mathbf{id}$ 도 넌터미널 연속이 없다.
다만 (a)와 같은 이유로 $L \to E$ 라는 단일 생성 규칙이 실용상 문제가 된다.

</details>

2. `+`(우선순위 1, 좌결합), `*`(2, 좌결합), `^`(3, **우결합**) 세 연산자에 대해
   $3 \times 3$ 우선 관계 표를 만들어라.

<details>
<summary>풀이</summary>

|  | `+` | `*` | `^` |
|---|---|---|---|
| **`+`** | ⋗ | ⋖ | ⋖ |
| **`*`** | ⋗ | ⋗ | ⋖ |
| **`^`** | ⋗ | ⋗ | **⋖** |

- 대각선 아래(왼쪽이 더 셈) → 전부 ⋗
- 대각선 위(오른쪽이 더 셈) → 전부 ⋖
- 대각선: `+`와 `*` 는 좌결합이므로 **⋗**,
  `^` 는 **우결합**이므로 **⋖**

`^` 행 `^` 열이 ⋖ 라는 것이 `2^3^2 = 2^(3^2)` 를 만든다.

</details>

3. 본문의 관계 표로 `( id + id ) * id` 를 파싱하는 과정을 표로 적어라.

<details>
<summary>풀이</summary>

| 스택 | 입력 | 관계 | 동작 |
|---|---|---|---|
| `$` | `( id + id ) * id $` | `$` ⋖ `(` | 이동 |
| `$ (` | `id + id ) * id $` | `(` ⋖ `id` | 이동 |
| `$ ( id` | `+ id ) * id $` | `id` ⋗ `+` | 축약 `E → id` |
| `$ ( E` | `+ id ) * id $` | `(` ⋖ `+` | 이동 |
| `$ ( E +` | `id ) * id $` | `+` ⋖ `id` | 이동 |
| `$ ( E + id` | `) * id $` | `id` ⋗ `)` | 축약 `E → id` |
| `$ ( E + E` | `) * id $` | `+` ⋗ `)` | 축약 `E → E + E` |
| `$ ( E` | `) * id $` | `(` ≐ `)` | 이동 |
| `$ ( E )` | `* id $` | `)` ⋗ `*` | 축약 `E → ( E )` |
| `$ E` | `* id $` | `$` ⋖ `*` | 이동 |
| `$ E *` | `id $` | `*` ⋖ `id` | 이동 |
| `$ E * id` | `$` | `id` ⋗ `$` | 축약 `E → id` |
| `$ E * E` | `$` | `*` ⋗ `$` | 축약 `E → E * E` |
| `$ E` | `$` | — | **수락** |

8행에서 `(` ≐ `)` 라 이동한다는 것, 그리고 9행에서
`( E )` 세 개가 한 핸들로 걷어내진다는 것이 ≐ 의 역할이다.

</details>

4. 우선 함수를 쓰면 `)` 다음에 `(` 가 오는 잘못된 입력을 왜 즉시
   걸러 내지 못하는지 설명하라.

<details>
<summary>풀이</summary>

원래 표에서 `)` 행 `(` 열은 **빈 칸**, 즉 "관계 없음 = 구문 오류"다.

우선 함수는 관계를 $f(a)$ 와 $g(b)$ 의 **정수 비교**로 표현한다.
정수 두 개는 언제나 `<`, `=`, `>` 중 하나이므로
**"관계 없음"이라는 상태를 표현할 수 없다**.

본문의 함수로 계산하면 $f()) = 6$, $g(() = 5$ 이므로
$6 > 5$ → `)` ⋗ `(` 로 읽힌다. 오류가 아니라 축약 지시가 된다.

결과적으로 파서는 잘못된 입력을 몇 단계 더 진행하다가,
축약할 핸들이 문법의 어느 규칙과도 맞지 않는 시점에서야 오류를 발견한다.
**오류 위치가 실제 오류 지점에서 멀어진다.**

</details>

5. 단항 마이너스가 왜 이 기법에서 문제가 되는지,
   `3 - -4` 와 `3 - 4` 를 예로 설명하라.

<details>
<summary>풀이</summary>

`3 - 4` 의 `-` 는 **이항 뺄셈**이고 우선순위가 낮다.
`3 - -4` 의 두 번째 `-` 는 **단항 부정**이고 우선순위가 아주 높아야 한다
(`-4` 가 먼저 하나의 값으로 묶여야 하므로).

그런데 우선 관계 표는 **터미널 하나당 행 하나, 열 하나**뿐이다.
같은 터미널 `-` 에 서로 다른 우선순위를 줄 방법이 없다.

`-` 행 `-` 열에 ⋗ 를 넣으면 `3 - -4` 가 깨지고,
⋖ 를 넣으면 `3 - 4 - 5` 가 우결합이 되어 `3 - (4 - 5)` 로 잘못 묶인다.

**해결:** 스캐너가 문맥(직전 토큰이 연산자였는지, 피연산자였는지)을 보고
단항 마이너스를 `UMINUS` 라는 **별개의 터미널**로 반환한다.
그러면 행·열이 따로 생겨 다른 우선순위를 줄 수 있다.

yacc의 `%prec UMINUS` 는 이것을 문법 쪽에서 해결한 것이다.

</details>

6. 연산자 우선순위 파싱으로 `stmt_list : /* 없음 */ | stmt_list stmt ;`
   같은 문법을 다룰 수 없는 이유를 두 가지 들어라.

<details>
<summary>풀이</summary>

**이유 1 — $\varepsilon$ 생성 규칙.**
`stmt_list : /* 없음 */` 은 $\varepsilon$ 규칙이다.
연산자 문법의 조건 1을 어긴다.

$\varepsilon$ 을 허용하면 "인접한 두 터미널" 사이에
아무것도 없는 넌터미널이 끼어들 수 있어, 관계 표가 어느 두 터미널의
관계인지 확정할 수 없게 된다.

**이유 2 — 넌터미널 연속.**
`stmt_list stmt` 는 넌터미널 둘이 **연속**한다. 조건 2 위반.

두 넌터미널 사이에 터미널이 없으면, 그 경계에서 어느 쪽이 먼저 묶이는지를
표시할 자리가 없다. 이 기법은 **터미널 사이의 관계**로만 핸들을 찾기 때문이다.

이것이 이 기법이 식 이외의 문법에 사실상 쓸 수 없는 이유이고,
LR이 필요한 이유다.

</details>

7. `examples/10-operator-precedence` 의 `PREC` 배열에서
   `+` 행 `*` 열을 `LT` 에서 `GT` 로 바꾸면
   `2 + 3 * 4` 의 값이 얼마가 되는가? 추적표로 설명하라.

<details>
<summary>풀이</summary>

**20 이 된다.**

바뀐 칸이 쓰이는 곳은 6단계 하나뿐이다.

| # | 스택 | 입력 | 관계 | 원래 | 바꾼 뒤 |
|---|---|---|---|---|---|
| 6 | `$ E + E` | `* 4 $` | `+` ? `*` | ⋖ → **이동** | ⋗ → **축약** |

⋗ 로 바뀌면 그 자리에서 `E + E` 를 걷어 내 축약한다.
스택이 `$ E` 가 되고, 남은 `* 4` 를 처리하면 `(2+3) * 4 = 20` 이다.

**추적표 전체**

| # | 스택 | 입력 | 관계 | 동작 |
|---|---|---|---|---|
| 1 | `$` | `2 + 3 * 4 $` | `$` ⋖ `num` | 이동 |
| 2 | `$ num` | `+ 3 * 4 $` | `num` ⋗ `+` | 축약 `E → num` |
| 3 | `$ E` | `+ 3 * 4 $` | `$` ⋖ `+` | 이동 |
| 4 | `$ E +` | `3 * 4 $` | `+` ⋖ `num` | 이동 |
| 5 | `$ E + num` | `* 4 $` | `num` ⋗ `*` | 축약 `E → num` |
| 6 | `$ E + E` | `* 4 $` | `+` **⋗** `*` | **축약 `E → E + E`** ← 여기가 달라졌다 |
| 7 | `$ E` | `* 4 $` | `$` ⋖ `*` | 이동 |
| 8 | `$ E *` | `4 $` | `*` ⋖ `num` | 이동 |
| 9 | `$ E * num` | `$` | `num` ⋗ `$` | 축약 `E → num` |
| 10 | `$ E * E` | `$` | `*` ⋗ `$` | 축약 `E → E * E` |
| 11 | `$ E` | `$` | — | 수락, 값 **20** |

**한 칸이 파스 트리를 바꿨다.**
`+` 와 `*` 의 우선순위가 뒤집힌 언어를 만든 셈이다.

이것이 [20장 `%left` 선언](/docs/yacc/conflicts-and-precedence#203-우선순위와-결합성-선언)이
하는 일과 정확히 같다 — 다만 yacc 는 이 표를
LR 표의 shift/reduce 결정으로 바꿔 넣는다.

</details>

표는 훨씬 커지지만, 실제 프로그래밍 언어의 문법을 그대로 다룰 수 있다.
